# Сценарий защиты Task Tracker

## Изолированная демонстрация

Не требуется изменять или перезагружать рабочую базу. В первом терминале из проекта бэкенда, при работающем PostgreSQL:

~~~powershell
cd C:\Users\kurap\PycharmProjects\task_tracker
.\.venv\Scripts\python.exe scripts/demo_server.py
~~~

Скрипт создаёт отдельную базу task_tracker_demo_<uuid>, заполняет её seed-данными и запускает API на порту 8002. Роль БД из .env должна иметь CREATEDB, как для тестов. Ctrl+C завершает сервер и удаляет только созданную временную базу. При аварийном завершении процесса автоматическая очистка может не выполниться.

Во втором терминале:

~~~powershell
cd C:\Users\kurap\PycharmProjects\task_tracker_frontend
$env:API_PROXY_TARGET = 'http://127.0.0.1:8002'
npm run dev
~~~

Откройте http://localhost:5173. Для возврата к обычному API остановите Vite, выполните Remove-Item Env:API_PROXY_TARGET и запустите снова.

Только для свежей демонстрационной базы (действуют 24 часа):

| Токен | Роль |
| --- | --- |
| test-admin-token | Администратор: пользователи и проекты |
| test-active-token | Руководитель проекта 1: работа с задачами |
| test-executor-token | Исполнитель user_id=3: переходы статуса назначенных задач |

Это существующие учебные токены из seed, не реальные секреты. В рабочей базе они могут быть просрочены.

## Показ CRUD пользователей

1. Подключитесь через «Сеанс» с test-admin-token.
2. Откройте «Пользователи». Выберите 5 записей на странице, нажмите «Вперёд» и «Назад».
3. Нажмите заголовок «Имя» дважды — порядок asc/desc отражается в URL и aria-sort.
4. Проверьте поиск и фильтр роли. Сбросьте фильтры.
5. Добавьте пользователя с новым логином и паролем от 8 символов. Сначала отправьте пустую форму — должны появиться ошибки.
6. Измените имя созданного пользователя. Пароль оставьте пустым.
7. Повторно создайте пользователя с тем же логином — должна появиться ошибка 409.
8. Нажмите «Удалить», затем «Отмена»: пользователь остаётся. Повторите удаление с подтверждением: пользователь исчезает, появляется success.
9. Попробуйте удалить seed-пользователя со связанными данными — покажите понятную ошибку 409.

## Показ CRUD проектов

1. Под администратором создайте проект с уникальным названием.
2. Отредактируйте название и описание.
3. Найдите его через поиск, проверьте сортировку и фильтр «Без задач».
4. Удалите этот пустой проект с подтверждением.
5. Существующий проект с участниками удалить нельзя: 409 сохраняет целостность данных.

Новый проект сам по себе не назначает участников. Для следующего сценария используйте подготовленный seed-проект 1.

## Показ CRUD задач

1. Смените сеанс на test-active-token.
2. Откройте «Задачи», проверьте фильтр ID проекта = 1, приоритет и статус.
3. Создайте задачу в проекте 1, выберите действующего исполнителя из списка, заполните название, описание, срок и приоритет. Новая задача имеет статус todo.
4. Отредактируйте название и описание (сохраняйте прежние статус, срок, приоритет и исполнителя).
5. Удалите созданную задачу с подтверждением. При изменении только текста история переходов не создаётся, удаление возможно.
6. Отдельно покажите переходы статусов: исполнитель переводит назначенную задачу todo → in_progress → in_review; руководитель принимает её или возвращает с обязательной причиной.
7. После изменения статуса у задачи появляется история. Удаление такой задачи должно вернуть 409 — это правило бэкенда, а не сбой интерфейса.

## Пустые состояния, ошибки и доступ

- Поиск случайной строки → пустая таблица с подсказкой.
- Неверный или истёкший токен → error notification и экран подключения.
- Руководитель открывает /users → сообщение о недостаточных правах.
- /users/999999/edit под администратором → ошибка 404 с возвратом к списку.
- Несуществующий маршрут → страница 404.
- Остановите API и обновите список → ошибка связи, уведомление и кнопка «Повторить». Запустите API и повторите запрос.
- Во время сохранения кнопка блокируется; при загрузке отображается spinner.
- Удалите последнюю запись второй страницы → список возвращается на предыдущую страницу.

Завершите демонстрацию Ctrl+C в обоих терминалах. Проверки перед защитой: npm test, npm run build, npm run lint и pytest бэкенда.
